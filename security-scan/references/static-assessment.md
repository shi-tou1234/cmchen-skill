# 静态发现评估

当必须用静态仓库证据来支持或否决某个候选时使用（动态复现被阻塞、代价不成比例或不可用）。这是验证的兜底——对大型内部仓库而言，它往往是首选方法。

## 评估元组

对每个论断，识别最小有用的元组：

- **source（来源）**：攻击者可控输入、外部触发，或可信操作者输入。
- **control（控制）**：相关 guard、验证器、消毒器、授权检查、配置开关、功能标志，或缺失的安全控制。
- **sink（汇点）**：危险操作、脆弱依赖、被破坏的控制，或影响点。
- **reachable path（可达路径）**：在所述前提下连接 source、control、sink 的代码/配置路径。
- **boundary（边界）**：使该路径具有安全相关性的产品面与信任边界。
- **counterevidence（反证）**：削弱、否决或限定该论断的静态事实。
- **proof gaps（证据缺口）**：缺少的、阻碍更强结论的事实。

不要只把"依赖存在、字符串匹配或部分调用链"当作完整评估。有用的静态评估既要说明发现了什么，也要说明还有什么未被证明。

## 证据搜索顺序

先检查最小的相关证据集，再扩大：

1. 用户提供的位置、扫描器位置、建议引用或 SARIF 结果位置。
2. 依赖清单、lockfile、包导出、二进制入口、构建元数据、部署配置与生成产物边界。
3. 受影响的函数、调用点、路由、RPC 处理器、解析器入口、CLI 命令、插件钩子、消息消费者与包 API。
4. 邻近的 guard、验证器、消毒器、授权检查、功能标志、配置检查与补偿控制。
5. 产品面证据：`SECURITY.md`、受支持版本文档、披露政策、威胁模型、产品文档、部署文件、注释与澄清意图的测试。

优先精确的仓库引用，而不是宽泛论断。若证据缺失，把缺失记录为证据缺口——除非缺失本身否决了该论断。

## 边界与表面检查

把静态路径视为安全相关之前，先分类：

- **产品面**：托管服务、库 API、CLI、本地开发者 UI、MCP/工具面、插件钩子、示例/demo、测试/fixture、文档、生成代码、内置（vendored）代码、未知。
- **来源可信度**：不可信用户输入、租户/用户控制数据、远程攻击者输入、可信操作者输入、可信开发者配置、仅本地输入、有意代码执行的扩展点、未知。
- **策略依据**：仓库策略、产品文档、部署/配置证据、包元数据、代码注释、威胁模型、未知。

检查不可信输入是否真能到达该 bug。

## 静态置信度

- **高**：精确的 source/control/sink 路径、明确的前提、相关边界证据、无实质性未决反证。
- **中**：有部分直接证据的可行路径，但调用链、配置、版本、部署或边界证据不完整。
- **低**：静态支持弱或间接、歧义显著，或缺少仓库上下文。

用证据缺口代替臆测缺失的运行时、环境、策略或部署事实。

## 输出要素

对每个候选记录：简明理由；已确立时的 source、control、sink 与可达路径；带精确 path:line 的受影响位置；边界评估与策略依据；支持证据；反证；证据缺口；基于静态证据质量的置信度；当静态证据无法定案时的最小下一步。
