# 验证指引

把发现阶段的候选变成最强证据支撑的验证评估。可行且代价成比例时，优先针对性、非交互的复现或证伪；动态执行被阻塞时，使用聚焦的静态追踪。

## 证据优先级链（最强可得方法优先）

按大致顺序选最强可用的方法：

1. **崩溃 PoC**：对崩溃 / 内存破坏 / 解析器混淆 / DoS 候选，当项目能以有界代价构建时，编一个调试变体并产出崩溃 PoC。
2. **valgrind / ASan**：若内存安全或崩溃候选不能立即复现，且构建支持，尝试 valgrind 和/或 ASan。
3. **调试器**：非交互式追踪，展示 source→sink 路径（`gdb -q -batch -ex run -ex bt -ex quit`、`lldb -b -o run -o bt -o quit`）。
4. **聚焦单元/集成测试**：添加或改写最小的、能触及脆弱代码并断言脆弱行为的测试。
5. **真实接口复现**：通过真实用户可达接口（HTTP、CLI、文件解析器、RPC、消息队列、插件钩子、包 API），用能到达可疑 sink 的构造输入做最小端到端复现。
6. **静态追踪**（见 `static-assessment.md`）：在有限尝试后动态复现仍不可行或不成比例时使用。对大型内部仓库，若运行需要不可用的服务/密钥/云账号，在元组完备后，用静态追踪加现有测试与部署/配置证据。**缺少内部运行时环境不是压制证据。**

当栈与范围允许时，用更强的方法，再回退到代码理解。命令保持简短、有界、非交互。创建 PoC 时，直接对真实应用/库触发它，以展示攻击者会如何触发该 bug。

## 保留实例的规则

- **逐个**验证每个候选实例。验证中保留候选 id、位置、instance 与发现证据。
- 某个重复高危模式中一个候选已具备强证明元组后，兄弟候选通过核验同一 source、最近控制、sink 与影响来验证。只有会改变可报告性、严重度或置信度时，才继续更深层的运行时工作。
- 不要因为代码是 demo、测试或只在本地运行就否定真实 bug。
- 构建/测试/环境错误不是即时反证。记录什么阻塞了运行时证明，然后当环境搭建不成比例时，用静态追踪加现有测试/配置。
- 不要只因一条长命令耗时就在有进展证据（输出、资源占用、产物、时间戳）时放弃它；结束前检查进程状态、日志与输出时间戳。
- 对不允许改动目标树的扫描，用一次性副本或生成产物目录放构建/PoC/测试夹具。

## 置信度校准

置信度由验证**方法与证据**决定，不由漏洞听起来多吓人决定：

- **高**：直接的源码、配置或运行时证据，无实质性未决阻塞。
- **中**：证据支持可行问题，但运行时行为、部署配置、角色可达性、类型约束或利用可靠性仍需证明。
- **低**：证据弱或不完整。

## 输出契约

对每个候选记录：判定（`reportable` 可报告 / `suppressed` 被压制 / `not_applicable` 不适用 / `deferred` 暂缓）、使用或建议的验证方法、观察到的证据、测了什么、剩余不确定性、若未验证时的确切证据缺口、还需更多证明时的最小下一步。`suppressed` 必须记录反证。不要暗示做过实际没做的验证。
