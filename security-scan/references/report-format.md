# 漏洞报告格式（Vulnerability Report Format）

写一份**自包含**的 Markdown 报告，读者是一名没见过原始 finding 的有经验安全工程师。报告读起来要像一位细心研究员带着另一位从受影响组件与攻击者前置条件，走到确切的漏洞源码、已证实影响与恰当修复。

语言与地区用用户要求的（未指定用其惯用默认），语气温暖专业、技术语言直接。用 "we" 引导真实推理：让同一个输入、对象或状态穿过相关摘录，并解释每步为何要紧。用 "I" 只陈述作者实际核对、构建、运行、观察或无法测试的东西。用平实语言解释应然行为与实际失败。

用一个具体文件名，例如 `freebsd-shm-ftruncate-uaf.md`。引用仓库相对路径、函数与已验证发布版本。给 fenced 源码摘录正确的语言标签。每个说明段落或列表项用一行自然源码；不要在一句话中间硬折 Markdown 散文。

## 证据与语气（Evidence and voice）

从证据出发，不从自信出发。把某 finding 叫可利用之前，先确立：被评估软件版本、配置、攻击者能力、可达路径、本应成立的安全行为、最窄的已证实边界跨越。用平实语言开场讲实际攻击：点名 Mallory 的合法起始凭据或输入、她跨越的独立所有者或策略、她到达的真实 sink。立即陈述重要的非主张，例如她复用的是自己的会话而非窃取他人或破坏某协议。把提供的笔记、未执行的 PoC、报告的 trace 当作论断，直到底层源码或运行产物被真正核对。

当经典命名角色能讲清故事时引入：Alice 是合法所有者，Bob 是另一位合法用户或预期接收者，Mallory 是主动攻击者，Eve 是被动窃听者。把 `alice`、`bob`、`mallory`、`eve` 带进示例账户名、请求、命令与 PoC 输出。只引入该漏洞实际需要的角色，并保留产品真实的账户角色与权限。

用自然散文保持"确切源码 / 已检查 PoC 代码 / 观察到的执行 / 提供的报告 / 推断 / 未知"之间的区别。不要机械地给每句加证据标签，也不要给每节加通用免责声明。

不要用 "witness" 描述支撑材料。说出读者能核查的具体东西：展示缺失检查的源码摘录、Mallory 对 Alice 文档的请求、泄露该文档的服务器响应、失败的测试、触发内存损坏的输入、抓到的执行 trace、观察到的 PoC 结果。解释该特定例子确立了什么。若真实源码符号或必需字段真的叫 `witness`，准确引用它并立即解释其实际用途。

把漏洞行为追溯到引入改动，核对发布 tag 与维护分支，验证修复发布或 backport。浅 checkout 能安全取得完整历史或确切发布归档时，不要就此结束调查。主要用公开版本号讲那段历史，并在能解释根因时说明引入改动本想修什么。只有对真实发布快照核对过后才给出首次受影响与首次修复发布。旧 tag、历史或分支覆盖不可用时，说"我能验证的最早版本"，不要编一个明确的受影响区间；点名未抽样的补丁发布或分支 tip，而不是暗示它们被检查过。

绝不编造受影响版本区间、引入日期、修复发布、部署普及度、默认配置、可靠竞态、root shell、租户跨越、CVE、CVSS 分数、日志或预期结果。文档化配置只证明配置存在，不证明多数部署启用它。受控时序测试只证明受控顺序，不证明生产可靠性。

避免抽象安全术语、宏大主张、戏剧性严重度语言、营销措辞、重复路标、空洞赞美、点缀式 "we can see" 句与脱节结论。描述"本该发生什么、实际发生什么、为何影响 Alice 或利于 Mallory"。优先选源码证明的确切小事实。

不要用 Git hash 填满报告。私下钉住确切源码，报告里引用公开软件版本与相关仓库相对路径；只有某具体引入/修复改动确实要紧、或没有已发布版本时，才提短 commit 引用。

分发的报告或 PoC 里**绝不包含作者机器的绝对文件系统路径**。适用散文、源码引用、链接、shell 命令、构建文件、注释、截图与抓取的终端输出。用仓库相对或报告相对路径，从包含材料里移除本地 home、临时、checkout 与 `file://` 路径。当描述或复现已验证漏洞必须时，保留目标系统绝对路径，如 `/etc/passwd`、`/proc`、`/dev` 或 Unix 域套接字。

最终报告必须**按顺序**包含以下七个标题。

## Executive Summary（执行摘要）

点名组件、被评估软件版本、所需攻击者位置、必要配置、易受攻击操作与最窄的已证实影响。源码历史与核对过的发布快照确立时，陈述已验证的首次受影响发布、受影响发布区间与修复发布。区分"最早核对过的发布"与"未经证实的首次受影响版本"，把"可能更强的效果"与"已证实的"分开。

第一段讲具体攻击及其限度，不要宣布一个笼统漏洞类。说出 Mallory 是谁、她以什么合法访问起步、哪道独立边界本该拦住她、实际发生了什么、以及这与会话窃取、协议缺陷或另一个诱人但无支撑的解释有何不同。

包含真实的验证依据第一人称陈述。例如：`我直接核对了受影响发布、其更早发布历史与修复；因为无一次性测试机，我未执行触发器。` 不要暗示源码核对复现了一个利用。

## Background（背景）

只介绍理解本 finding 所需的组件行为、命名角色、受控值、归属、特权边界与应然安全行为。把完整已测拓扑与前置条件放靠前。把默认行为与可选配置、部署假设分开，不猜普及度。

攻击涉及相似对象或值时，具体命名并在全文保持该区别。例如区分 `alice` 的文档与 Mallory 已认证的 `mallory` 会话。只有摘录确立了真实入口点、安全边界或正常行为时，才放短源码摘录。

## Vulnerability Details（漏洞详情）

按因果顺序跟随所报告触发器。从 Mallory 实际受控输入开始。有源码时核对每个实质检查或状态改变，展示代码在确切哪行未能强制应然行为。用户明确接受无源码的"仅报告"评估时，把所提供触发序列描述为有条件，指出其实际证据与不可用检查，绝不编造源码摘录、行或观察状态。先确立任何已验证的普通策略或归属检查，再描述有证据的共享状态、接收组件或依赖决策与下游操作，不把未验证论断升级。让同一个请求、对象、字段或状态穿过整条路径。命名角色不符合实际机制时，描述真实角色，不强套示例。

对每个可用、已验证的源码摘录，标明其仓库相对源码路径、函数与被评估软件版本。对运行时测试过的厂商/发行包，按确切已打补丁源码验证摘录与行号；不要把邻近的上游 tag 当作跑过的代码。按因果顺序引用可用依赖代码，用平实英语解释具体日志或 trace 字段。只引确立决定性行为所需的行，然后解释它们证明了什么、还有哪些未验证；明确接受的"仅报告"评估无源码时，完全省略源码摘录。用实际是什么来指代每个演示，如 `Mallory 的请求`、`返回的文档`、`失败的测试` 或 `执行 trace`，不要用未解释的证据标签。处理相关校验、锁、取消、清理、权限、时序与替代解释，而不是假定它们挡不住该路径。

发布历史可得时，解释漏洞行为如何进入项目、哪些已发布版本含它；否则指出缺失历史，不要猜受影响发布。仅当引入或修复对解释实质相关时，才用 commit 引用。

若确切源码与所声称序列矛盾，明确说出。不要悄悄用附近更弱的 bug 或更方便的测试事件替换 finding。

## Exploitability Analysis（可利用性分析）

从证据实际确立的**窄原语**开始。解释它能在已验证前置条件下跨越哪个账户、特权、租户、进程、内存对象或可用性边界。

只在底层源码或授权实验支撑其前提时，讨论更强利用路径。解释有意义的约束，如分配器行为、可控字节、协议顺序、配置、调度与清理。未证实的可能链条或时序窗口标为有条件。

有授权一次性目标或已验证执行 trace 时，加入排除最强替代解释的正/负向控制：展示正常允许的访问、跨越边界处的新鲜拒绝、相关时的同域成功、仅攻击到达的真实 sink、以及任何实际测过的一设置缓解。解释每个观察到的控制排除了什么。无执行或已验证 trace 时，把相关控制描述为未执行的验证工作，而非暗示有运行观察。不要把普通可达性变成远程代码执行、人为交错变成生产可靠性、或不同身份变成提权。

## Proof of Concept（概念验证）

标明真实 PoC 产物、目标要求、构建步骤、执行安全与预期状态。使用一致的示例账户名，如 `alice`、`mallory`。区分：确切源码核对 / 保留的运行记录 / 离线证据核对 / 检查过的 PoC 代码 / 成功的语法或构建检查 / 拼装但未运行的便利复现器 / 源码确认的发布 / 实际观察到的运行。

从可分发报告目录使用相对命令，例如：

```sh
cd poc
make
./poc
```

只有作者生成的或直接核对过的 trace 里的命令输出才能写。解释每个请求、响应、测试运行或输出行实际展示了什么，而不是叫它 "witness"。从真实抓取输出里移除本地绝对路径而不编造结果；必要且要紧时显式标出一个必要省略。执行不可用或不安全时说明原因；把未观察结果明确描述为预期行为，而非成功运行。绝不伪造崩溃、shell、泄露值、日志或固定目标结果。

说明任何清理，并清楚警告 PoC 可能损坏数据、耗尽资源、崩溃机器或改变权限。无法安全开发真实 PoC 时，解释该限制，不编造产物。

## Remediation（修复）

用平实英语说明修复后的代码必须做什么：例如在返回给已登录用户前检查所请求文档属于 Alice；或仅当当前生效认证策略也接受记录里的身份时，才接受恢复会话。点名每个必须保持独立的策略输入，在序列化或恢复时保持该区别，并在需要时把它放进共享查找键。周围源码支持时给一个小型、源码兼容的提议修复，或引用并解释已核对的上游修复。清楚区分提议的修复与已实际发布的修复，已知时标出已验证修复发布。

建议覆盖真实入口点、失败状态转移、有意义负向控制与合适时邻近变体的回归测试。只有加固能处理已证实机制时才建议更宽的加固。

## Summary（总结）

重述已验证前置条件、实际安全失败、受影响版本与已证实影响，不升级任何先前的有条件论断。仅当有证据基础时，简要指出最有用的剩余验证、利用问题或相关源码路径。

报告与同级 `poc/` 目录里的每个文件都必须在作者环境之外可理解。检查所有 Markdown、源码、脚本、构建配方与包含的输出，找出个人机器与其它本地绝对路径。不包含内部存储位置、扫描器实现细节、起草流程或占位符。最终披露包还含独立 advisory 时，保持其格式分离，并通过隔离的临时目录或链接验证技术报告，使 advisory 不会被误认为第二份技术报告。
