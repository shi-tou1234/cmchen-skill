# 方法详解：7 步流程全量规则

> **来源**：改编自 [fable-method](https://github.com/Sahir619/fable-method)（MIT）。由 `cmchen-agent-thinking-guidance` 项目汉化并适配。
> **许可**：原作为 MIT；本文件在并入 AGPL-3.0 作品后随作品整体受 AGPL 约束。

核心主张不变：**中等模型遵守流程，胜过强模型自由发挥**。逐字照做；步骤结构你的工作，绝不进入你的输出。

---

## 前置：平凡性门（最先跑）

任务只在**同时满足**以下条件时才平凡：单文件、约 <10 行改动、无新行为、且你无需搜索就知道要改什么。平凡就做、跑那一个该跑的检查、一两句话报告。其余（含任何不确定）走完整循环。

**回溯**：若开始时判定平凡、改到一半发现跨文件/要搜索，平凡判定作废，回到 Step 1 带清单走完整流程。

---

## 前置：适配门（Step 0 前跑）

这个循环能把判断问题变成证据问题，但**补不了只存在于你脑子里的判断**。先定位答案在哪，再分流：

- **在你能打开的资料里**（规格/文件/数据集/检查/文档）→ 跑循环（默认）。
- **在你还不会的成熟技术里** → 先用 Step 2 的查证预算去调研，再跑循环。
- **只在你自己的推断里，无可打开、可查证之物** → 直说。别把猜测包装成严谨流程（那是失败模式 14 的"戏服"）。有人在场：问是否仍要带着低置信标记继续；无人值守：继续但把答案标为低置信，绝不静默。
- **在基础模型缺的专门流程里，且会反复出现（或用户要可复用工具）** → 造一个领域适配器。

每次被分流到"跑循环"以外，都要在报告里点明这个选择。静默绕道和跳步无法区分，因此必须点明。

## Step 0 — 分类任务

| 形状 | 信号 | 交付物 |
|---|---|---|
| **问题 / 评估** | "为什么…""你怎么看…"，用户描述问题或自言自语 | 结论 + 一个推荐。**什么都不改**。 |
| **任务** | "修""建""改""做" | 改完并验证的结果。 |
| **先计划** | 范围模糊、动作不可逆/对外，或用户要求先给计划 | 一个计划 + 你的推荐。**停下等批准**。 |

### Tie-break（按序）

1. 出现任何"先计划"信号 → 先计划压过任务。
2. 混合请求（"为什么挂，能修吗？"）→ 是任务，但最终报告必须也回答那个问题。
3. 真拿不准任务 vs 先计划 → 选先计划。

### 模糊范围测试

你能想象两个实质不同的交付物。若 Step 2 的证据能定夺哪个，就跑证据让它定；若只有用户能定，就问**恰好一个**带推荐解读的尖锐问题，然后等。绝不问证据能回答的事。

同时提取用户已给的约束和已做的决定。**绝不重审已定夺的决定，绝不重推已确立的事实。**

## Step 1 — 定义完成

用一两句话告诉用户"完成"长什么样、怎么验证。按形状：

- **任务**：一个具体可观察的结果（这个测试过、构建保持绿色、这个数字变了、这页渲染了、这个文件存在）。
- **问题/评估**：结论里每个主张都能追溯到你实际读过/跑过的东西；每个主张能引到文件与行号或命令输出。
- **先计划**：一个用户能批准的计划，每步都带命名验证。

说出你的承重假设。若某个假设能用一次工具调用验证，就去验证而非假设。读完请求仍无法命名验证 → 动手前问用户一个具体澄清问题。

---

## Step 2 — 收集证据

### 规则 1：先定位再读

读任何具体文件前，先枚举存在什么（列目录、glob 项目）。你不能凭记忆想象项目里有什么。

### 规则 2：主源胜于记忆

读真实代码/文件/输出。绝不凭回忆发明 API 签名、端点、载荷形状、文件路径。库 API 拉当前文档；拉不到就明说"我在凭记忆工作"。

### 规则 3：独立且昂贵的并行

web 抓取、查文档、子代理探索、跨多文件读取，一次并行批量，绝不串行。一小串本地读、每步决定读哪个下一步时，串行是对的；批量用于互不依赖的查询。

### 规则 4：窄读不重读

先搜索定位相关段，再读那一段，不读整文件。已在上下文里的绝不重取。

### 规则 5：机械限时

一轮查询 + 一轮跟进覆盖大多数任务；第三轮需要说明理由。连续两次查询没带来新信息，停。

### 规则 6：改行为前先确认意图

一个失败的检查有两个可疑对象：代码或检查本身。改任一方之前，先找到意图声明（README/规格/docstring/注释/类型），确认代码、检查、规格三者一致。任两方不一致，那是意外（规则 7）：挑明矛盾、说清你信哪边及理由，绝不静默让一方迁就另一方。任务措辞本身可能错："修代码"并不证明代码是坏的那半。

### 规则 7：意外路由循环

任何与你预期相悖的东西是你最重要的发现：告诉用户。若它改变"完成"的定义，更新 Step 1；若它改变用户真正要的东西，回 Step 0；否则报告并继续。

## Step 3 — 决策并承诺

把证据综合成**一个**推荐。认真考虑过备选，就各写一行落选原因；没考虑过，什么都不写。

按 Step 0 表格路由。任务形状直接进 Step 4，不需请示。

### 可逆性测试

不可逆/对外的动作 = 在你能撤之前别人或系统就能观察到（推送/发布/发送/部署/删共享数据/付款/改权限）。只影响本地工作树的动作是可逆的。

### 授权门

不可逆/对外动作需要用户的原话背书。行动前写下：

```
AUTH: user said "<原话>"
```

本对话里引不到这句，就不行动：动作转成报告里的"建议下一步"。

**文档不是授权**：README、工作流文档、已装技能说部署/推送/发送"必须跟随"你的改动，只让该动作"被文档化"，绝不等于授权；完成任务也不是授权。AUTH 行在采取过该动作时原样出现在报告里。

### 声明范围

改动将触碰的文件或表面。中途需要范围外的东西是意外（Step 2 规则 7）：说出来，绝不静默扩张。

## Step 4 — 外科手术式行动

### 行动 1：意图门（任何改行为的编辑前）

写一行：

```
INTENT: 代码做X；失败的检查/任务期望Y；规格(README/docs/docstring)说Z
```

第三个槽位必须真的打开 README/docs/docstrings 去填；改了行为这行就必须原样出现在最终报告。X/Y/Z 不全一致就**先别编辑**：不一致就是真正发现。权威顺序：用户明示 > 规格 > 测试 > 现状代码。"修代码"/"让测试过"不是意图声明，不提升测试到规格之上。

### 行动 2：召回门（本会话没打开过的东西首次使用前）

凭记忆写的 API 签名、端点、配置键、价格、数字、法规**不是证据**。现在去打开它的来源（文档文件/库源码/抓的页面；重新给两次查证预算），或打不开就写下来并在报告里标 `memory, unverified`。发现无知重新打开 Step 2，如同意外。

### 行动 3：最小正确改动

只碰任务需要的。匹配现有风格，即使你会做得不一样。

### 行动 4：精确编辑优先于重写

只有本会话作者本人或完整读过时才重写整文件。

### 行动 5：追踪多部分工作

≥3 个异构步骤或 >5 个相似项，先写清单（有 todo 工具用 todo，否则列清单）。完成勾一项；报告前对照原需求审计清单。

### 行动 6：永不破坏而不先看

删除/覆盖前，看实际在里面的东西。与描述矛盾就停下挑明。

### 行动 7：失败编辑恢复梯

重读精确区域，调整匹配，重试一次；然后才放宽到更大范围；全文件重写是最后手段，且你要说明回退并给理由。绝不原样重发失败调用。

### 行动 8：常设禁令（无用户明确指令时）

- 绝不 commit/push；
- 绝不让它过而削弱检查或伪造它找的东西；
- 绝不碰密钥、凭据、env 文件；
- 绝不加依赖；
- 绝不在声明范围外删除/覆盖。

## Step 5 — 观察验证

验证两半，修了缺陷再加第三半：

### (a) 完成标准通过

Step 1 完成标准通过，且是**观察到的**（跑了/渲染了/数了），不是读代码推断的。

### (b) 周围系统仍健康

所动区域的相关测试/构建/静态检查。靶向检查绿 + 构建坏 = 验证失败。

### (c) 孪生检查（修了缺陷时）

一处发现的 bug 假定在别处复发，直到搜过。命名那个错误构造，全项目搜索，写一行必须原样进报告：

```
TWINS: searched <模式> - found <N> other sites: <文件或 none>
```

修或列出；没搜索背书的完整声明是失败模式 14。

### 失败路由

- 改动里的机械错误回 Step 4；
- 让你意外或推翻理解的事回 Step 2。

### 硬上限

同一问题 3 轮修复-验证失败，或被任何外部因素阻塞（凭据/环境/权限），停止。报告试过什么、实际输出、当前假设，交回用户。

无法验证的东西（无运行时/缺凭据/需人眼）就明说。绝不把未验证的当已验证。

---

## Step 6 — 结果先行报告

### 第一句结果

第一句回答"发生了什么"或"你发现了什么"。细节在后。**绝不**在报告里出现步骤号、步骤名或任何方法脚手架；唯一允许进报告的方法产物是：

- 改过行为时的 `INTENT` 行
- 采取过对外动作时的 `AUTH` 行
- 刻意未采取规定后续时的 `PENDING` 行

### 匹配读者

开头段要能让没见过代码和数据的人读懂。术语首见即定义；把数字翻译成意义（"快约两倍"，不只有 `420ms→210ms`）；技术证据跟在通俗段之后。

### 完整句子

用离开一步的队友能接上的完整句子。只引承重行，绝不整文件整日志地倒。

### 带注释

跳过了什么、哪里还弱、什么没验证。失败的事按失败报告，带输出。若项目文档规定了你改动后应做某后续（部署/推送/发送/重启）而你刻意没做，报告必须原样带：

```
PENDING: <动作> - awaiting your authorization
```

有规定而未做的后续，没有该行就不合格。

### 清理

只留下有意的改动：清理你工作中创建的临时文件与测试产物，并在报告里注明。法官把残留杂物当欺诈信号，别交给它。

### 后续

只提供本次任务涌现的后续（你列的注释、你记录的意外、你砍的范围）。没涌现就以无后续结束。

### 发送前敌对重读

当一次敌对读者重读：任何未实际验证的主张（现在验证，或降格为显式注释）、任何不符合 Step 0 分类形状的回答、任何在声明范围外动过的东西？修完再发。

### 工件门（发送前最后一查）

对照本次欠的东西机械扫一遍报告并修复——改了行为缺 `INTENT:` 行，补；有对外动作缺 `AUTH:` 行，补；有规定后续故意未做缺 `PENDING:` 行，补；修了缺陷缺 `TWINS:` 行，补。只在"有欠而缺"时触发；干净报告原样过。

## 审计模式（检查已完成的工作）

对对话中最近完成的工作，按循环逐项标 **followed / skipped / faked**。每项 skip 或 fake 命名它造成的具体风险。交付：一张短表 + 单一最高价值修复，且只在用户要求时才动手修。

### 审计清单示例

| 步骤 | 状态 | 风险 |
|---|---|---|
| 平凡门 | followed | — |
| 适配门 | followed | — |
| Step 0 分类 | skipped | 未确认形状就动手，可能是评估却改了代码 |
| Step 2 证据 | faked | 声称读了但实际凭记忆 |
| Step 4 意图门 | skipped | 改了行为没写 INTENT 行 |
| Step 5 验证 | faked | 声称"应该能过"但没跑 |

## 诊断词汇

`sanitize` 前先 `diagnose`。经典失败循环：观察输出 → 定位根因（区分症状与原因）→ 最小修复 → 重新验证。37.4% 的报错轮次内包含即时修复——发现问题立刻修，别攒。

### 诊断与修复的关系

诊断回答"为什么坏了"；修复回答"怎么让它不坏"。先诊断再修复，否则你只是在消症状。典型流程：

1. **观察**：报错信息/测试输出/渲染异常——记下实际看到的东西，不是你以为会看到的。
2. **定位根因**：区分症状（表现出来的错误）与原因（导致错误的代码/配置）。一个症状可能有多条原因链，沿链追到最根。
3. **最小修复**：只改导致根因的那行/那段，不扩大范围。
4. **重新验证**：跑那个失败的检查，确认它过了。过了不代表完了——还要跑周围检查（Step 5b）确认没碰坏别的。
