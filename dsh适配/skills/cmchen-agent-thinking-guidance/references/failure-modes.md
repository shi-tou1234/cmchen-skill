# 失败模式：症状 → 步骤

> **来源**：改编自 [fable-method](https://github.com/Sahir619/fable-method) 的 `references/failure-modes.md`（MIT 许可）。原始内容为英文，本文件已全面汉化改编，并入 AGPL-3.0 作品后随整体受 AGPL 约束。
>
> **用途**：18 种 agent 工作出错的方式，每种从外部看是什么样，由循环的哪一步防住。用于审计（`method.md` 审计模式）命名跳步造成的风险；单独也能当任何 agent 记录的复查清单。

agent 在真实任务中最常翻车的 18 种方式。每一条不是抽象理论，而是你在读一份 agent 工作记录时能直接看到的外部症状——然后告诉你协议的哪一步设计来防住它。这张表有两个用法：

1. **当复查清单**：做完一份工作后，逐行扫一遍，看自己有没有犯。
2. **当审计语言**：审一份 agent 记录时，不要说"感觉不对"——命名它犯了哪条，然后指出哪一步被跳过了。

## 18 种失败模式

| 编号 | 失败模式名称 | 症状（外部看到的样子） | 由哪步防住 |
|---|---|---|---|
| 1 | **未经请求就动手** | 用户问"为什么"；agent 却改了文件。用户要诊断，得到的是改动。 | Step 0：问题形状只交付结论，不改动任何东西。 |
| 2 | **猜错交付物** | agent 建了解读 A（比如写了一份报告）；用户要的其实是 B（比如改一行代码）。 | Step 0：模糊范围测试——一个带推荐解读的尖锐问题。 |
| 3 | **重审已定决定** | 用户已经做过某个选择（比如"用 PostgreSQL"），agent 又把"该不该用 MySQL"拿出来重新推一遍。 | Step 0：提取已做的决定；绝不重推已定决策。 |
| 4 | **虚假"完成"** | agent 说"完成了"，但没人（包括 agent 自己）能说出结果到底怎么被验证过。 | Step 1：动手前完成带命名的验证定义。 |
| 5 | **凭空发明 API** | 代码调用了不存在的端点或用了错误的函数签名——agent 从记忆里编出来的。 | Step 2.2 主源胜于记忆；Step 4.2 首次使用时的记忆门。 |
| 6 | **串行爬行** | 一次只发一个查询，等结果，再发下一个。长任务永远跑不完，token 白烧在等待上。 | Step 2.3：独立查询一次批量；整工作单元用子代理。 |
| 7 | **上下文淹没** | 整个文件、整个日志原封不动倒进对话窗口。关键信息被噪音淹没。 | Step 2.4 窄读不重读；只引承重行。 |
| 8 | **分析瘫痪** | 查证不再改变计划，却还在继续查。查了三轮以上，每轮都没有改变下一步动作。 | Step 2.5：两轮之后要么给理由要么停。 |
| 9 | **强行穿过意外** | 证据推翻了计划（比如发现 API 签名和预期不同），agent 仍按原计划逼着前进。 | Step 2.7：意外被陈述并重路由循环。 |
| 10 | **选项倾倒报告** | "你能做 A、B、C"——列了一堆选项，没有一个推荐。用户被迫自己选。 | Step 3：一个推荐；备选各一行写掉为什么落选。 |
| 11 | **越界改动** | 顺手重构了不相关的代码、改了代码风格、做了"没人要的改进"。 | Step 4.3 最小正确改动；Step 3 声明范围。 |
| 12 | **静默跳步** | 需求清单有 9 项，报告说"全部完成"，但第 7 项悄悄从没发生过。 | Step 4.5：书面清单，报告前对照需求审计。 |
| 13 | **重试空转** | 同一个失败的修复换着小变化永远在试。改了一行、跑、失败、改回来再试另一个变体——没有出口。 | Step 5：路由重试，3 轮硬上限，带输出与假设交回用户。 |
| 14 | **验证表演** | "现在应该能行了"却什么都没真正跑；或者靶向检查绿了但整个构建是坏的。 | Step 5：观察验证，两个半边（靶向 + 周围系统）。 |
| 15 | **未授权对外动作** | 没人要的部署、推送、发送、安装。"README 说要部署的"不是授权。 | Step 3：授权门；无引述用户授权，无动作。 |
| 16 | **静默丢弃后续** | 项目文档规定改动后应部署或重启；报告从头到尾不提这个决定，好像它不存在。 | Step 6：刻意未做的规定后续永远是带注释的待授权项。 |
| 17 | **漏掉孪生** | 缺陷只在报告的那一处修好，相同的副本还活在项目的其他地方。没搜就宣布"完成"。 | Step 5(c)：孪生检查，强制 `TWINS:` 行命名模式并全项目搜。 |
| 18 | **戏服式严谨** | 周全的外形（因素列表、自信的"全部清楚"）背后没有搜索或检查。规则催"要严谨"时最容易犯这条。 | Step 5(c) 强制搜索被命名且可重跑；适配门把纯判断任务路由到诚实的"这是猜"。 |

## 怎么读一份审计

审计的核心任务不是检查"每步都做了吗"，而是检查**声称做了的步骤有没有被真正执行**。一张审计表把每一步标成 `done`、`skipped` 或 `faked`：

- 标为 **skipped**（跳过）的步骤制造其行里的风险。跳过 Step 2 意味着失败模式 5/6/7/8/9 的风险全部打开。
- 标为 **faked**（伪造）的更糟：记录声称该步骤发生过（通常是失败模式 4、5、6），但观察缺失——那是失败模式 14（验证表演）披着循环当戏服。审计的职责就是抓戏服。

**faked 比 skipped 危险得多**。skipped 是"我知道我没做"，faked 是"我假装做了"。前者可以补，后者是信任的彻底坍塌。

### 代价最高的三种失败

如果一份审计只能查三件事，就查这三件：

1. **失败模式 1——未经请求就动手**：用户问"为什么"，agent 改了文件。这摧毁的不是代码，是用户对 agent 的基本信任。一旦信任崩塌，后面所有工作都需要额外验证，成本指数级上升。防住它的成本极低（Step 0 分类时看一眼请求是问题还是任务），但漏掉的代价极高。

2. **失败模式 13——重试空转**：同一个失败的修复换着小变化永远在试。它烧的是时间和 token，而且没有自然出口——agent 不会自己停下来，会一直试到用户失去耐心手动打断。3 轮硬上限就是防这条：三轮失败后必须停下来，交回"试了什么、实际输出、当前假设"，把决策权还给用户。

3. **失败模式 14——验证表演**：最危险的一条。"现在应该能行了"——但什么都没跑。或者跑了靶向测试绿了，但整个构建是坏的。它把坏活贴上"完成"的标签发出去，让用户在部署后才发现问题。防住它的方法也只有一条：观察验证（跑出真实输出），而且两个半边都要看（靶向检查 + 周围系统健康）。

这三种失败的共同点：它们都不是"做错了"，而是**做了不该做的、或没做该做的却声称做了**。防住它们的不是更强的推理能力，而是更强的纪律——分类、硬上限、观察验证。这也是为什么本协议的核心主张是"一个遵守流程的中等模型，胜过自由发挥的强模型"。

### 审计实操建议

拿到一份 agent 工作记录后，按以下顺序检查：

1. **先看报告第一句**：它回答了用户的问题吗？如果用户问"为什么慢"而第一句是"我修改了..."，直接标失败模式 1。
2. **找验证输出**：报告里有没有真实跑出的输出（测试通过数、命令返回值）？没有就标失败模式 14。
3. **数重试次数**：同一个问题修了几次？超过 3 次且没交回用户，标失败模式 13。
4. **扫门禁痕迹**：`INTENT:`、`AUTH:`、`TWINS:`、`PENDING:` 在该出现的地方出现了吗？缺失意味着对应门禁被跳过。
5. **对照需求清单**：用户要的每一条都完成了吗？有没有静默消失的条目？有就标失败模式 12。

这五步覆盖了代价最高的失败模式，且每步只需要几秒钟。
