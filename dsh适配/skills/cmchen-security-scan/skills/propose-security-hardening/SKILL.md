# 结构性安全加固（Propose Security Hardening）

把一组安全证据变成**可直接决策的结构性/架构性加固机会组合（portfolio）**。证据可以是：一次安全扫描（进行中或已完成）、普通漏洞披露文档、提供的 findings、事件或评估材料、相关源码，或它们的混合。把证据当支撑与进一步源码核对的线索。产出物要能让资深安全工程师拿去开设计评审：有意义的选项、改造前后图、明确取舍、迁移计划与实施交接。

**不要求必须有一份安全扫描。** 一个披露文档目录就是合法输入，直接分析即可。**不要求先有扫描封印**：自动最终报告阶段时规范文档尚未封印，照常分析。有已完成扫描的完整性元数据时，把它当额外证据；有任何不匹配或缺失产物就报告为局限，不要因此拒绝有用的输入。

保持三种产物的区分：

- 规范扫描产物与其它提供的证据**只读**；
- 加固分析是派生的、可修订的设计产物；
- 实现改动只在用户选定某选项并**明确让 Claude 改仓库之后**发生。

不要把加固分析变成又一份漏洞报告，也不要把漂亮架构图当成 finding 已修复的证明。

先定位本技能所在目录（`<SKILL_DIR>`，即 bundle 内 `skills/propose-security-hardening/`）。共享的 scripts 与 references 在 `<BUNDLE_ROOT>` = `<SKILL_DIR>`（DSH 中 `<SKILL_DIR>` 即本 skill 的 base directory）；本模式的格式契约在 `<BUNDLE_ROOT>/references/proposal-format.md`。

## 语气

用资深安全工程师给同行写设计提案的自然声音：专业温和、精确、对不确定性坦诚、乐于听取意见。实质推理全程用第一人称复数（"我们可以保住快路径"、"如果我们选这条边界"）。第一人称单数要真实且克制，用于建立作者的分析基础与建议（"我核对了这些调用者"、"我没能验证设备暴露"、"在当前约束下我建议选项 2"）。绝不编造个人观察、测试或测量。

这不是代词配额。不要给机械散文撒 "we"/"I"。第一人称要暴露推理、把读者请进设计选择、让作者的证据基础可审计。只有首尾两句第一人称的提案仍算不合格。

让专业判断显出来：这个选项吸引人之处、让作者犹豫之处、哪个取舍看似相称、哪个未知阻止了更强结论。语气要贴合实际设计，不要在组合里重复套话。

## 接受的输入

从一个或多个开始：

- 一个目录或显式列表的漏洞披露、粗报告、提供的 findings、事件评审、评估文档、PoC、trace 或其它相关产物
- 一个扫描目录（含其规范 `scan-manifest.json`、`findings.json`、`coverage.json` 与可用的详细 finding 报告）
- 可得时的目标源码树与相关修订/快照
- 用户对性能、内存、兼容性、可靠性、运维复杂度、交付周期或变更预算的任何约束

不要因为集合缺扫描 manifest、finding JSON、coverage 回执、扫描 ID 或封印就阻塞。把缺失的源码身份、覆盖、复现或目标上下文记为证据局限，相应收窄论断。用户要"源码可验证的结论"但没有源码或确切修订时，解释这个更窄的局限，而不要把整个集合误标为无效扫描。

绝不修改源码证据或已封印产物。派生输出写到分析目录（默认 `<scan_dir>/hardening/` 或用户指定位置），这些是派生的、未封印的。**实现改动**只有等用户选定选项并明确要求后才发生。

## 工作流

### 1. 核对并准备证据

按实际存在的产物选输入模式。

扫描：直接核对规范 manifest、findings、coverage、详细报告与被引源码。自动最终报告阶段时这些文档可能还在封印前状态，把它们当当前规范证据，验证与封印留给正常扫描完成。已完成扫描：相关契约工具可用时检查记录的产物 hash 与源码身份。不要声称"已封印完整"，除非那些检查通过；但别把封印变成设计分析的前提。

披露文档或其它提供的产物：不要去找或要求扫描元数据。直接盘点每个输入文件/目录，分配稳定的证据 ID，记录路径、面向读者的简洁标题、标签，可行时记录 hash。把紧凑盘点写进 `<hardening_dir>/context.md`，然后读相关披露、finding、PoC、trace 与源码文件本身。混合输入时，让扫描证据与补充文档可区分；不要把未封印目录伪装成已封印扫描，也不因它不是扫描而拒绝有用文档。

确定确切修订/快照时，确认源码树代表它。若当前工作树已移动，用已识别修订分析证据并单独记录漂移。无不可变源码身份时把漂移记为 `unknown` 并说明局限；绝不编造修订，也不把当前代码说成受影响快照。

读生成的 context、详细披露或 finding 报告、威胁模型（若有）与相关源码（若有）。抓到的片段只是线索；在把源码作为支撑的架构论断前，重新打开相关边界周围的源码。

### 2. 建立机会清单

按**被违反的不变量、信任边界、控制所有者、危险能力、状态转移、重复的预防性控制**聚类证据。不要只按 CWE、严重度、目录或标题聚类。

至少满足以下一条时，才把某个加固机会算作合格：

- 多个 finding/披露源自同一个分散或归属不一致的安全控制
- 一个高影响 finding/披露暴露了可信扼制点，且有可信的复发或爆炸半径风险
- 核对过的源码显示一个重要不变量只靠约定编码
- 威胁模型与覆盖回执显示某组件过度特权或隔离边界薄弱，且与存活的 finding 直接相关
- 多个战术修复在重复同一预防性控制

仅凭通用最佳实践、猜测性重写或无关清理的提案要拒绝或暂缓。**结论"这些 finding 相互独立、按比例的局部修复更合适"是合法结果。**

充分展开少数最高杠杆的机会。低置信想法列为暂缓，别稀释主提案。

若无机会合格，记录 `local_remediation_preferred` 评估与空的机会列表，解释为什么战术修复按比例即可——不要因为分析是自动跑的，就硬造一个架构提案。

### 3. 绘制当前设计

对每个合格机会追踪：

- 攻击者可控入口点与信任边界
- 拥有或重复该控制的组件
- 流入特权操作的数据、权限、生命周期或状态
- 部署与运行时边界
- 失败遏制与恢复行为
- 性能关键或分配敏感路径
- 兼容义务与运维依赖

已知时引用确切 finding/披露证据、报告、函数、类型、路径与源码修订。区分 `Observed` / `Inferred` / `Proposed`。提供的报告可支撑推断，但不证明重设计后每个预期性质。

把证据 ID 当交叉引用键而非读者向名称。不要要求读者记得 `E021` 或 `csf_...` 这样的不透明 ID 在 `context.md` 里的含义。在每个提案里，用它的简洁 finding/文档标题与它确立了什么是定义每个引用的 ID。保留 ID 可追溯，但读者用到它时，旁边放上人类可懂的含义。

### 4. 定义期望的不变量与约束

把设计必须使之更易保持的安全性质写成**可证伪的行为不变量**，例如：

- 每个归档条目目标都在一个专属提取边界内派生并检查，然后才写文件系统
- 不可信插件代码无法获得环境凭据或任意网络权限
- 授权策略在解析完所有别名与重定向后，只对最终资源身份求值一次

记录非目标、兼容要求、发布约束与未知的性能/内存预算。用户没给优先级时，用平衡画像并把该假设显式写明，不要用一个问卷来阻塞。

### 5. 展开真正不同的选项

需要时把"当前结构 + 更强的局部控制"作为基线来澄清决策。然后只做真正不同的替代，例如：

- 把强制收敛到一个专属 API 或安全表示
- 用 capability 或作用域句柄移除环境权限
- 引入进程、服务、租户或特权分离
- 重设计状态机，使非法转移不可表示
- 把策略移到中央决策点，同时保留本地强制

不要强行凑选项数，不要制造表面变体。通常两三个严肃替代加基线就够了。某个貌似显然的选项被拒时，若对审阅者重要，解释原因。

读者向选项从 1 编号。基线仍是请审阅者考虑的第一个选项，不是"选项 0"。机器向 `optionId` 保持语义化且稳定，不从显示顺序派生。

在比较或推荐前，先用编号与描述性标题逐个介绍每个选项。执行摘要里让完整选项集一眼可见，并把选项与发布步骤区分开。不要把带编号的短实现清单放在编号不同的选项旁边，以免读者把步骤误当成选项集。

### 6. 评估安全与工程取舍

对每个选项至少覆盖：

- 安全效果与残余攻击面
- 性能与延迟
- 内存与资源消耗
- 可靠性、可用性与故障隔离
- 运维与可观测性负担
- 兼容性与迁移复杂度
- 开发者体验与控制漂移可能性
- 可逆性与回滚

为每个取舍记录：期望方向、置信度、依据、测量或验证计划。`measured` 只用于实际得到的结果；否则用 `source-derived` / `analogous` / `hypothetical`。不要编百分比、把比较压成一个不可解释的分数、或把未知藏在自信的形容词后。

把每个相关 finding/披露证据项映射到每个选项的 `addresses` / `mitigates` / `unaffected` / `unknown`，并说明迁移期间或迁移后其战术补丁是否仍必要。

### 7. 画可比较的改造前后图

当图在实质上澄清信任边界、控制归属、权限流或故障遏制时，用 Mermaid flowcharts。前后视图保持在相同抽象层，尽量复用组件名与布局。

只显示安全相关结构。每组图后跟一张含 `Change`、`Before`、`After`、`Security consequence`、`Cost` 的 delta 表。绝不把图当成源码支撑解释的替代品。

### 8. 写 portfolio

动笔前**完整读** `<BUNDLE_ROOT>/references/proposal-format.md`，把它的叙述验收标准当产物契约而非可选风格建议。产出：

- `hardening.json`：结构化的证据身份、约束、评估结果、机会、证据、选项、取舍与建议
- `hardening.md`：简洁的 portfolio 与决策摘要
- `proposals/<opportunity-id>.md`：每个合格机会一份完整技术提案；评估结果为局部修复时省略该目录
- `diagrams/<opportunity-id>-before.mmd` 与每个选项的 after 图
- `implementation/<option-id>.md`：仅在用户选定选项或明确要求实施计划后

用仓库相对源码路径与分析相对产物链接。可分发的提案文件里不要放本地绝对路径或内部起草溯源。

让读者向证据引用自包含。`hardening.md` 的机会表里用简洁证据标题或带标签的组，而非裸 ID。每个提案的证据引用引入为 `<ID> (<简洁标题>)`，证据覆盖行同时标 ID 与简洁标题。`context.md` 里的完整登记是可审计材料，但不能替代读者实际使用处的证据定义。

把必需标题、表格与图当作可读叙述的支撑。解释每块为何要紧，把证据连到结构诊断，在比较前逐个讨论每个严肃选项。对每个选项带读者走一遍：什么保持不变、什么变化、为何改变的边界提升安全、风险留在哪里、重要的性能/内存/可靠性/运维成本怎么产生、项目如何引入或逆转该改动。保留必需表格：它们是可扫描、可比较的第二层。图表前后都要用散文解释，别让产物独自扛论证。让建议清晰但不丑化替代。说出什么会让另一选项更好，把不确定沉在平静散文里而非藏进标签。

复杂选项要有真正展开的讨论，不只是图与表周围一句引言加一句结论。它的散文要能独立成立：给出设计的最强理由与工作原理；推演安全收益与残余风险；讨论物质资源与可靠性效应背后的机制；描述可信的采用、验证与回滚姿态。在可能改变决策的取舍上花最多篇幅。简单或中性点可简洁，但简洁不是工程判断的替代品。

### 9. 评审与验证

通盘检查：重复的机会、无支撑的架构论断、不一致的图、未检查的关键路径、只是重命名同一设计的选项。

再以设计评审参与者身份审查文字。以下要拒并重写：只有点缀式第一人称、从证据跳到建议却不走推断、把选项压缩成图+表+短摘要、把取舍留成标签而不解释机制。确认一个技术强但对子系统陌生的人，能理解机会为何存在、为每个严肃选项做最强论证、看到哪些事实或优先级会改变建议。不要为了变长而加填充；加的是让决策舒适、可审所需的讨论。

把提案放一起审。当重复的"我们需要决定"开头或一句话的选项结论让 portfolio 像机器拼装时，重写它们。真核对过源码时，在每个提案里用真实的第一人称陈述让这一分析基础可见，别只留在 portfolio 索引里。确认每个表周围的段落解释重要比较，而非只是宣告表存在。

拒绝任何在不透明 finding/证据 ID 旁没有邻近人类可读标题或同文档早前定义的读者向文档。检查 portfolio 表、证据讨论、选项覆盖表、迁移计划与验证计划；只存在于 `context.md` 的映射不过关。

对照 `<BUNDLE_ROOT>/references/proposal-format.md` 直接检查每个必需产物：`hardening.json` 能解析、ID 与交叉引用一致、相对链接在分析目录内、每个合格机会有提案与可比较图、所有必需取舍维度已覆盖、`hardening/hardening.md` 在挂靠扫描时是常规文件。可用时跑相关仓库格式化/lint 检查。这些检查通过或每个剩余局限被清楚解释前，不交接。

### 10. 呈现决策，然后审慎推进

先讲机会组合、当前假设下的建议、与最影响决策的取舍。链接可读 portfolio、结构化分析与提案文件。

请用户选择选项、细化约束、组合兼容元素或拒绝诊断。提案里含实施工作包不等于要改源码。

用户选定某选项并要求实施后：

1. 刷新目标源码，有记录目标修订/快照摘要时与它比较
2. 报告实质性漂移，编码前更新提案
3. 把所选选项变成有序工作包：明确验收标准、发布、回滚、测试与基准
4. 保留迁移期间需要的战术防护
5. 分可审阶段实现，并对照结果代码验证映射的 findings

## 质量线

一份好的加固 portfolio：

- 锚定到已识别、完整性记录的证据与（可得时）已核对源码
- 解释架构为何促成或放大了观察到的失败
- 区分事实、推断与提案
- 提供真实选择，无"选项表演"
- 让安全、性能、内存、可靠性、迁移与运维取舍可读
- 用可比较的图与精确的改动清单
- 点名残余风险与仍需的战术修复
- 无需重新发现设计即可转成实施工作
- 局部修复优于架构改动时保持诚实
- 耐心把技术强的读者从观察证据带到共享结构状态、可用选择、取舍与决策
- 听上去专业、温和、人类，实质走查用 "we"，真实 "I" 陈述建立检查、验证、不确定与建议
- 用表与子弹做比较与参考，不让它们替代技术叙述
- 公平呈现替代，即使建议某选项，也说明每者何时可能正确
- 给每个选项足够连贯散文解释其机制、安全后果、残余风险、资源成本、发布与回滚
- 让作者的判断可见（吸引点、顾虑、未知），不啰嗦也不戏剧化
- 避免复杂选项与提案间重复的"引言-图-表-结论"节奏
- 让每个不透明证据标识符在它出现的文档里可懂，同时保留标识符可追溯
- 说出什么证据、约束或优先级会改变建议

**设计实现并对原始漏洞路径重新验证之前，绝不声称提案修复或关闭了某个 finding。**
