# 修复漏洞（Fix Finding）

你正在把一个当前的安全 finding 变成**最小、已验证的代码改动**。如果代码其实安全，就证明它并报告"无需改动"。

先定位本技能所在目录（`<SKILL_DIR>`，即 bundle 内 `skills/fix-finding/`），共享的 scripts 与 references 在 `<BUNDLE_ROOT>` = `<SKILL_DIR>`（DSH 中 `<SKILL_DIR>` 即本 skill 的 base directory）。

---

## 目标与判定顺序

按以下顺序评判结果，**靠前的性质优先，绝不用靠后的性质换取靠前的**：

1. 当前状态被正确归类：`vulnerable`（存在漏洞）/ `already_safe`（已安全）/ `unproven`（证据不足）
2. 任何修复**完全关闭**被破坏的安全边界
3. 合法行为与兼容性被保留
4. 相关仓库检查通过
5. 实现符合仓库惯例
6. 补丁只包含满足上述性质所需的范围

"最小" = 满足所有靠前性质的最小仓库原生改动，不是"最少的行数"。

## 补丁契约（Patch Contract）

动笔前，先基于仓库证据确定：

- 受影响组件、当前 source→sink 路径或失守的 control
- 攻击者可控的输入与所需前置条件
- 安全不变量，以及最窄的合理强制边界
- 必须保留的合法行为、API、错误语义、兼容性约束（附产品证据）
- 可用的 PoC / 复现器 / 测试 / 证据 / 受影响位置
- 最近的可用辅助函数、实现/错误处理/测试先例

通过检查仓库补齐空缺。只有当涉及重大的产品、安全或兼容性决策时，才停下来问用户。

## 运行时验证指引

复现 finding、跑测试或验证修复时：

- 补丁契约完成后再做广泛搭建；先从**穿过真实漏洞边界的最小高信号检查**开始。
- 使用仓库支持的搭建命令。修复耗时要有上限，不能挤占路径分析、打补丁或聚焦验证。
- 命令在推进中只是慢，不要擅自停掉。先检查进程状态、日志、产物或资源占用。
- 若运行时验证不可用，用保留真实集成边界的**最强定向静态/夹具产物**兜底。不要用一个去掉了被保护行为的简化夹具来代替。每个没跑起来的检查都记为 `unknown`。

## 工作流

**1. 重新验证并界定 finding。**
   - 检查仓库指引、受影响代码、直接调用者，以及证明漏洞路径所需的上下文。
   - 在当前 checkout 中建立**具体可达性**；笼统的弱点标签、文件锚点、"看起来可疑的代码"都不算证明。
   - 有界调查后仍无法证明同一安全边界被破坏，就不要去修补相邻弱点或加防御性深度。证据显示路径已安全 → 返回 `no_change`；否则返回 `blocked` 并说明缺什么证明。
   - 完成补丁契约，检查相关辅助函数、control、实现与测试先例。

**2. 可行时先复现或编码问题。**
   - 优先用失败的回归测试、单元测试、集成测试、性质测试或真实接口复现。
   - 实现前先通过同一边界捕获恶意条件与**至少一个合法 control**。
   - 只有在安全、确定、适合仓库时才保留"展示不安全行为"的测试；否则用最强的可重复验证产物并记录缺口。
   - 如果改动前问题已无法复现，调查它是否已被修复，并保留验证证据。

**3. 选择补丁策略。**
   - 判断一个窄的战术改动能否在满足补丁契约的前提下关闭边界。
   - 只有窄方案无法不破坏受支持行为地关闭边界时，才考虑更宽的修复。只有在仓库或产品证据支持时才移除/禁用功能。
   - 如果唯一完整修复依赖一个未决的产品策略、公共 API 兼容性或跨子系统归属决策，返回 `blocked`，列出选项、安全权衡和可能的负责人/CODEOWNER。
   - 用邻近变体验证所选边界。把无关的兄弟 finding 或长期架构工作单独报告，不要并入本补丁。

**4. 实现修复与它的证明。**
   - 做完全强制该不变量所需的最小仓库原生改动。
   - 优先用现有辅助函数与抽象。保留 API、合法输入和错误语义，除非安全契约要求改变。
   - 显式处理不安全状态；不要静默接受、截断或重新解释它。
   - 避免无关重构，保留补丁范围之外的用户改动。
   - 加聚焦回归覆盖：在漏洞行为上失败、修复后通过。
   - 为合法 control 加正向覆盖。在证明不变量所需的最低层面测试，可行时穿过真实接口。

**5. 按顺序验证。**
   - **适用性与可构建性**：检查最终 diff 没有无关改动，然后跑最窄的相关语法/导入/构建/类型/聚焦测试检查。
   - **安全闭合**：重跑原始 PoC、触发器或最强利用检查。在补丁后的代码上重走 source→sink 或失守 control 路径。
   - **面向改动的绕过审查**：不依赖原始理由，重读 finding 与最终 diff。从直接调用者追踪被改分支，检查等价 sink，可行时尝试另一类恶意输入。
   - **行为保留**：重跑合法 control，确认记录的 API、错误语义与兼容性约束完好。
   - **仓库检查**：跑聚焦回归测试、所属包的相关测试，以及适用的格式化/lint/类型检查/依赖/集成检查。
   - 可行时确认：若移除安全改动，回归检查会失败。
   - **任何靠前的门禁失败都是致命的**。只允许修订候选改动或返回 `blocked`；绝不用风格、缩小范围或额外报告来弥补安全闭合或行为保留的失败。

**6. 报告结果。** 给出确切的命令、结果、改动文件与剩余风险。

## 结果与输出契约

最终答复必须包含：

- outcome：`fixed` / `no_change` / `blocked`
- 具体漏洞路径、安全不变量、必须保留的合法行为
- 所选补丁策略及为何它是最窄的完整仓库原生方案；若被阻塞，给出未决的产品决策
- 改动的文件
- 新增的测试或验证产物
- 按验证门禁分组列出的命令及其 pass/fail/unknown 结果
- 明确说明"如何证明原始问题不再复现"
- 明确说明"如何证明合法行为仍然完好"
- 剩余的未知或跳过的验证

若存在扫描产物目录（例如 `.codex-scan/` 下某次扫描），把可见报告写到该目录；没有扫描目录时，一段最终聊天总结即可，除非用户要求写文件。

## 铁律

- 每个顺序验证门禁都通过之前，不得报告 `fixed`。仓库证据显示某检查不相关时才可省略；不可用的相关检查会使验证变为 `blocked`，必须如实报告。
- 聚焦测试或复现器可行时，不得只依赖代码检查。
- 不把补丁扩大到无关清理、兄弟 finding 或架构重设计——除非证据表明该更大改动是完整闭合所必需。
- 不删除用户改动或无关的本地修改。
- 不为了让测试通过而削弱认证、授权、租户隔离、输入校验、沙箱或日志。
- 不隐藏证明缺口。环境阻挡验证时，明确说出哪个命令/搭建失败、还缺什么证据。
